# IUoC caching decision

Reviewed 2026-11-17. Scope: the Next.js website and its Convex catalogue, not the mobile app. Local baseline: `6f84e39` plus the unpublished repository-readiness changes. No production traffic or billing measurements were collected.

## Decision

Keep Convex's built-in query caching. Do not add a persistent Next.js catalogue cache solely because refreshing sends requests. There is no measured performance or cost problem establishing that another cache is needed. This supersedes the initial suggestion that the website should add an extra cache.

## Official guidance

- Convex caches query results and refreshes them when their database dependencies change. Cache hits avoid database bandwidth charges. This does not mean refreshing creates no network traffic or that every aspect of serving a request is free. [Realtime](https://docs.convex.dev/realtime), [Queries](https://docs.convex.dev/functions/query-functions).
- Convex documents `fetchQuery` for non-reactive server-rendered data and `preloadQuery` with `usePreloadedQuery` when server rendering must transition into a reactive client subscription. Its documented preloading intentionally uses `no-store`. That policy concerns Next.js rendering/caching; it does not disable the backend query cache. [Next.js server rendering](https://docs.convex.dev/client/nextjs/app-router/server-rendering).
- Convex's React client maintains a backend connection for query subscriptions. A fresh page establishes a new client connection; avoiding all refresh requests is a different requirement from avoiding repeated database computation. [React overview](https://docs.convex.dev/client/react/overview).
- Explicit calls and subscription updates are relevant to usage accounting. Query caching should not be described as eliminating all usage or providing abuse protection. [Limits](https://docs.convex.dev/production/state/limits).

## Local observations

- Installed versions: Convex 1.50.0 and Next.js 16.4.6. The Convex SDK's `node_modules/convex/src/nextjs/index.ts` sets `cache: "no-store"` in `setupClient` for server calls.
- `app/page.tsx` loads featured videos, latest videos and visible playlists through three parallel queries. These stable arguments are suitable for Convex's automatic caching; actual production hit rates were not measured.
- `components/ConvexClientProvider.tsx` creates one client per loaded application, rather than a client per component render. `components/video-explorer.tsx` uses native query/pagination subscriptions and skips inactive search/filter queries.
- The catalogue routes declare `revalidate = 3600`, but their uncached SDK fetches leave these routes dynamic in the local production build. This declaration is not evidence of an hourly page cache and is not needed for Convex's own cache to work.
- `convex/crons.ts` schedules ingestion four times daily. Public catalogue reads query stored documents; refreshing does not invoke ingestion or consume YouTube Data API quota. Embedded YouTube playback and thumbnail requests are separate from our ingestion API key.
- `lib/daily/use-resource.ts` keeps recent reading resources in an in-memory map. It does not persist across full refreshes. That alone is not a defect.
- Video and series detail routes repeat their entity lookup in metadata and page rendering. This is a candidate for request-scoped deduplication if profiling shows a meaningful benefit, not evidence that the database is repeatedly recomputing the result.

## Tradeoffs and follow-up criteria

1. Retain native Convex caching and subscriptions now. No runtime caching changes are justified by this investigation.
2. If cost, latency or traffic becomes a concern, inspect production function usage, query cache hits and response timings first. Compare repeated identical reads with cache misses following a catalogue update; do not infer cache misses from network requests alone.
3. Consider request-scoped deduplication before a persistent cache if duplicate detail lookups materially affect request counts or latency. Verify metadata and page content remain consistent.
4. Consider a persistent Next.js/CDN cache only if measurements show a benefit worth implementing invalidation after ingestion. Verify new, updated and removed videos, series totals, metadata and search remain coherent after imports. An arbitrary TTL can otherwise leave server content older than reactive client content.
